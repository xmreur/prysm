# Prysm Relay Protocol v1 (`prysm-relay/1`)

Authoritative implementation contract. Everything below is normative: the protocol package, the
server, the client adapter and the docs MUST match it. Wire format decisions trace back to the
decision tickets in `.scratch/relay/issues/`.

Design in one paragraph: a **Relay** stores **sealed** blobs in a **Mailbox** until the owner picks
them up. Each contact of the owner deposits at its **own opaque address**, so the Relay learns
neither who sends nor which contact an address belongs to — it does know which **owner** every
address and item belongs to, because pickup is authenticated and `index.json` maps
`deposit -> ownerFingerprint`. The sealed payload is the *original, unmodified* Prysm message
envelope, so on pickup the client feeds it to `InboundMessageRouter.handleMessage` byte-identical and
the whole inbound pipeline (auth, dedup, `pending_auth`, FTS, notifications) runs unchanged.

## 0. Vocabulary and constants

| name | value |
|---|---|
| protocol id | `prysm-relay/1` |
| transport | HTTP/1.1 over a Tor v3 hidden service, port 80, JSON bodies (UTF-8) |
| deposit address | 32 random bytes, lowercase hex (64 chars), generated by the **owner** |
| owner id | Ed25519+X25519 identity **fingerprint** (hex SHA-256, as `IdentityKeyPair.fingerprint`) |
| seal scheme | `relay-sealed-1` |
| seal HKDF info | `prysm-relay-seal-1` |
| auth context | `prysm-relay-auth-1` |
| advertisement context | `prysm-relay-advert-1` |
| pair context | `prysm-relay-pair-1` |
| contract context | `prysm-relay-contract-1` |
| clock skew | ±300 s |
| replay window | 600 s (server keeps seen signature digests) |

All binary fields are base64 (standard, with padding) unless the table says hex.

## 1. Seal (`relay-sealed-1`)

Client-side only; the Relay never opens it. Implemented in `packages/prysm_relay_protocol`
(`RelaySeal`), **not** in `lib/crypto`, so the app's crypto surface is untouched.

```
seal(plaintext, recipientAgreePublic /* X25519, 32B */) ->
  { "crypto":"v2", "scheme":"relay-sealed-1", "alg":"x25519-hkdf-aes256gcm",
    "ephemeralPub":"<b64 32B>", "nonce":"<b64 12B>", "ciphertext":"<b64>" }
```

- ephemeral X25519 keypair per seal; shared secret with the recipient's long-term X25519 agreement key;
- `HKDF-SHA256(secret, salt = ephemeralPub, info = utf8("prysm-relay-seal-1"))` -> 32-byte AES key;
- `AES-256-GCM`, 12-byte random nonce, AAD = `utf8("prysm-relay-seal-1|relay-sealed-1|x25519-hkdf-aes256gcm")`;
- **no outer signature**: authenticity of the content is already carried by the inner envelope
  (ratchet AEAD/AAD, `dm-signed-*`, `group-sender-1`); an outer signature would let an operator test
  candidate public keys and confirm "X wrote this", which is exactly what the seal buys.
- The HKDF info differs from `hkdfInfoDhAead`, so a sealed blob can never be confused with, or
  replayed into, the 1:1 DM path (domain separation).

Plaintext = `utf8(jsonEncode(originalEnvelope))` where `originalEnvelope` is the exact map the client
would have POSTed to `/message`: `{id, senderId, receiverId, message, type, timestamp[, replyTo,
fileName, fileSize, viewOnce, forwarded, expiresAt, groupId]}`. `receiverId` MUST remain the
recipient's own onion or `_validateAddressedToLocal` rejects it with 403 on pickup.

## 2. Advertisement (how a sender learns where to deposit)

Published by the owner's client in the **per-requester** `GET /profile?requester=<onion>` body under
key `relay`. Per-requester is what makes per-contact addresses possible without a new message type.

```json
"relay": {
  "v": 1,
  "issuedAt": 1789200000000,
  "expiresAt": 1791792000000,
  "relays": [
    { "onion": "<56>.onion", "deposit": "<64 hex>", "maxItemBytes": 1048576, "blockSize": 0 }
  ],
  "sig": "<b64 Ed25519>"
}
```

- `sig` covers
  `utf8("prysm-relay-advert-1|<ownerFingerprint>|<issuedAt>|<expiresAt>|<relay0.onion>|<relay0.deposit>|<relay0.maxItemBytes>|<relay0.blockSize>|…")`
  — every field of every endpoint, in wire order, `|`-joined — signed with the owner's Ed25519
  identity key. A cached advertisement is therefore verifiable offline, which is the whole point:
  it is used precisely when the owner is unreachable. `maxItemBytes` and `blockSize` are inside the
  signature because they decide whether the sender relays at all and how it pads.
- The list is ordered and MAY hold several relays; **v1 clients publish and use exactly one**
  (redundancy is fog). The array exists now because changing it later would break the wire.
- `blockSize` 0 = no padding in v1; declared now so padding can be switched on without a breaking
  change.
- Sender-side cache: `users.relayAdvertisement` (TEXT, JSON) in `chat_app.db`, written by
  `PeerIdentityResolver` on every successful profile fetch. Expired or absent -> no relay delivery.
- The owner's client MUST NOT publish the advertisement to requesters it would redact today
  (unknown/blocked): the advertisement inherits `buildProfile`'s redaction policy.

## 3. Endpoints

All responses are JSON. Errors: `{"error":"<code>","message":"<human>"}` with the HTTP status from
§3.9. Unknown path -> 404 `not_found`.

### 3.1 `GET /relay/manifest` (public)

```json
{ "protocol":"prysm-relay/1",
  "relayIdentityJson":"{\"crypto\":\"v2\",\"signPublic\":\"<b64>\",\"agreePublic\":\"<b64>\",\"fingerprint\":\"<hex>\"}",
  "relayFingerprint":"<hex>", "relayOnion":"<56>.onion",
  "tenancy":"private"|"public", "admission":"closed"|"invite"|"open",
  "limits":{ "maxItemBytes":1048576, "maxMailboxItems":256, "maxTenantBytes":268435456,
             "itemTtlSeconds":1728000, "maxMailboxes":512, "pickupBatchItems":64,
             "pickupBatchBytes":8388608, "blockSize":0 },
  "terms":"<free text, may be empty>", "software":"prysm-relay/<version>",
  "issuedAt":<ms>, "sig":"<b64 Ed25519 over utf8('prysm-relay-manifest-1|'+canonical json of the fields above minus sig)>" }
```

Signed so the app can show the user *who* it is pairing with and what it promises before any
Contract exists. `relayIdentityJson` is **required**: a fingerprint alone is a claim, and without the
public key neither this manifest nor the Contract signature could be verified by anybody.
`RelayManifest.fromJson` rejects a manifest whose `relayFingerprint` disagrees with the embedded
identity, and `manifest.verifySelf()` performs parse + fingerprint match + signature check in one
call. Fingerprints are hex SHA-256 over `signPublic || agreePublic` (`RelayIdentity.fingerprintOf`),
identical to the app's own rule, so the two sides cannot drift.

### 3.2 `POST /relay/pair`

Body: `{ "protocol":"prysm-relay/1", "token":"<hex setup/invite token>",
`         "ownerIdentityJson":"<the exact /public identity JSON>", "ownerOnion":"<56>.onion",`
`         "requested":{ "maxItemBytes":…, "itemTtlSeconds":…, "maxMailboxes":… },`
`         "timestamp":<ms>, "sig":"<b64>" }`

`sig` over `utf8("prysm-relay-pair-1|<relayFingerprint>|<ownerFingerprint>|<token>|<timestamp>")`.

Server: validates protocol, token (single use, unexpired), identity JSON (recomputes the
fingerprint — same rule as `IdentityKeyPair.parsePeerIdentity`), skew, signature; clamps `requested`
to its own limits; creates the tenant; returns the **Contract** (§4). Re-pairing with the same
identity and a fresh token is idempotent: it returns the existing Contract with a new `version`.

### 3.3 `POST /relay/mailbox` (owner-authenticated)

Body: `{ "op":"put"|"disable"|"delete"|"list", "deposit":"<64 hex>",
`         "label":"<opaque client-side label, optional, max 64 B>",`
`         "maxItems":<int, optional>, "maxBytes":<int, optional> }`

- `put` registers or updates a deposit address (rotation = `put` new + `delete` old). The address is
  generated by the owner: 32 random bytes make collisions a non-issue and keep the Relay from
  inventing capabilities.
- `maxItems`/`maxBytes` MAY only **tighten** the Contract: a value above `maxMailboxItems` or
  `maxTenantBytes` is rejected with `bad_request`, so the owner learns immediately. That check is
  not sufficient on its own — a renewal MAY lower `maxMailboxItems` while the stored policy keeps
  the wider value (re-pair preserves mailboxes) — so the deposit path MUST enforce
  `min(policy.maxItems, maxMailboxItems)`. A stale `maxBytes` needs no clamp: `maxTenantBytes` is
  enforced on every deposit anyway.
- `disable` keeps stored items but refuses new deposits (`mailbox_disabled`).
- `delete` removes the address and its items.
- `list` returns `{"mailboxes":[{"deposit":…,"label":…,"items":N,"bytes":N,"enabled":bool,
  "oldestExpiresAt":<ms|null>}]}`.

The set of registered addresses **is** the whitelist: revoking a contact is `delete`, and the Relay
never learns which human that address belonged to (`label` is opaque to it and MAY be omitted).

### 3.4 `POST /relay/deposit` (capability-authenticated)

Body: `{ "protocol":"prysm-relay/1", "deposit":"<64 hex>", "payload":{<sealed envelope §1>} }`

Authorization is knowledge of `deposit` — the Signal delivery-token pattern. The sender is never
identified to the Relay and never signs.

Response 200: `{ "status":"stored", "itemId":"<uuid>", "expiresAt":<ms> }`.

Server MUST: reject unknown/disabled addresses with `mailbox_unknown` (404 — deliberately the same
answer for "never existed" and "revoked", so probing learns nothing); enforce `maxItemBytes`,
`maxMailboxItems`, `maxTenantBytes`, per-address rate limit; store the payload verbatim.

### 3.5 `POST /relay/pickup` (owner-authenticated)

Body: `{ "protocol":"prysm-relay/1", "max":<int optional> }`
Response: `{ "items":[ {"itemId":"<uuid>","deposit":"<64 hex>","storedAt":<ms>,"expiresAt":<ms>,
             "payload":{…}} ], "more":bool, "usage":{"items":N,"bytes":N} }`

Ordered by `storedAt` ascending, capped by `pickupBatchItems`/`pickupBatchBytes`. Pickup is
**non-destructive**: items live until acked (§3.6), so a client that crashes mid-pickup loses
nothing. `more:true` means call again.

### 3.6 `POST /relay/ack` (owner-authenticated)

Body: `{ "protocol":"prysm-relay/1", "itemIds":["<uuid>",…] }` ->
`{ "deleted":N, "unknown":M }`. Deleting an already-deleted item is not an error.

### 3.7 `POST /relay/status` (owner-authenticated)

`{ "contract":{…§4}, "usage":{"items":N,"bytes":N,"mailboxes":N,"oldestExpiresAt":<ms|null>},
   "limits":{…}, "serverTime":<ms> }`

### 3.8 `POST /relay/unpair` (owner-authenticated)

`{ "confirm":true }` -> `{ "status":"unpaired", "deletedItems":N }`. Deletes tenant, mailboxes and
items. Irreversible by design: the point is to leave nothing behind.

### 3.9 Owner authentication

Every owner-authenticated request carries headers:

```
X-Prysm-Owner:      <ownerFingerprint hex>
X-Prysm-Timestamp:  <unix ms>
X-Prysm-Signature:  <b64 Ed25519>
```

Signature over
`utf8("prysm-relay-auth-1|<relayFingerprint>|<ownerFingerprint>|<method> <path>|<timestampMs>|<sha256hex(body)>")`.
The Relay MUST reject: skew > 300 s (`stale_request`), unknown owner (`not_paired`), bad signature
(`bad_signature`), and a signature digest already seen inside the replay window (`replayed`).

| code | HTTP | retryable by sender |
|---|---|---|
| `bad_request` | 400 | no |
| `bad_signature` | 403 | no |
| `not_paired` | 403 | no |
| `stale_request` | 401 | yes (clock) |
| `replayed` | 409 | no |
| `mailbox_unknown` | 404 | no |
| `mailbox_disabled` | 403 | no |
| `item_too_large` | 413 | no |
| `mailbox_full` | 507 | **yes** |
| `tenant_full` | 507 | **yes** |
| `rate_limited` | 429 | **yes** |
| `admission_closed` | 403 | no |
| `bad_token` | 403 | no |
| `internal` | 500 | **yes** |

Retryable means the client keeps the message in its local pending queue and tries again later;
non-retryable means relay delivery is abandoned for that message (it stays queued for *direct*
delivery, exactly as today).

## 4. Contract

```json
{ "protocol":"prysm-relay/1", "version":1,
  "relayFingerprint":"<hex>", "relayOnion":"<56>.onion",
  "ownerFingerprint":"<hex>", "ownerOnion":"<56>.onion",
  "tenancy":"private"|"public",
  "limits":{ …the full RelayLimits object, as in §3.1… },
  "overflow":"reject",
  "issuedAt":<ms>, "expiresAt":<ms|null>,
  "sig":"<b64 Ed25519 by the relay>" }
```

`sig` over `utf8("prysm-relay-contract-1|"+<canonical JSON of every field except sig>)`, where
canonical JSON = keys sorted lexicographically, no whitespace. The client stores the Contract and
shows its limits; it MUST refuse a Contract whose `relayFingerprint` does not match the manifest it
paired against.

`overflow:"reject"` is the only v1 policy: a full Mailbox refuses new deposits (`mailbox_full`,
retryable) rather than silently dropping the oldest message. Losing the newest message is visible to
the sender; losing the oldest is visible to nobody. A Contract carrying any other value MUST be
refused (`bad_request`), never read as `reject`: a relay that announces `drop-oldest` is promising a
policy the client cannot enforce.

## 5. Server config and storage

`relay.yaml`-free by design: a single JSON config, because the server must not drag in a YAML parser.

```json
{ "onion": "<56>.onion", "bind": "127.0.0.1", "port": 8443,
  "dataDir": "/var/lib/prysm-relay",
  "tenancy": "private", "admission": "invite",
  "allowedOwners": ["<fingerprint hex>"],
  "limits": { …as §3.1… },
  "rate": { "depositPerMinute": 60, "pickupPerMinute": 30, "pairPerHour": 10 },
  "logLevel": "counters"
}
```

`bind` MUST be a loopback address: the only reachable surface of a Relay is its hidden service, so
a routable listener is refused at config load (`init` and `serve` both).

Storage is the filesystem — no SQLite, no native dependency, so `dart compile exe` yields a truly
standalone binary:

```
<dataDir>/
  identity.json                  relay Ed25519 keypair (0600)
  tokens.json                    setup/invite tokens: {token, createdAt, expiresAt, usedBy?}
  tokens.json.lock               held for every read-modify-write of tokens.json
  init.lock                      held for the whole of `init`
  index.json                     deposit(hex) -> ownerFingerprint
  tenants/<ownerFingerprint>/
    contract.json
    mailboxes/<deposit-hex>/
      policy.json                {label?, enabled, maxItems?, maxBytes?}
      items/<itemId>.json        {itemId, storedAt, expiresAt, size, payload:{…}}
```

- All writes are write-to-temp + `rename` (atomic), mirroring the app's own HS-key handling. The
  temp name MUST be unique per writer (`<file>.<pid>.<n>.tmp`): a shared name makes two concurrent
  writers rename each other's file away.
- `tokens.json` MUST be read-modify-written under an exclusive `tokens.json.lock`: `token new` runs
  in a different process from `serve`, and both rewrite the whole file. The lock MUST also exclude
  *inside* the process: `fcntl` locks belong to the process, so two `/pair` handlers (or a handler
  and the sweeper) otherwise run the read-modify-write at once and the staler of two overlapping
  writes can be renamed last, dropping a `usedBy` and making a single-use token work again after a
  restart. Same for `init.lock`.
- `init` MUST hold an exclusive `init.lock` across its conflict checks (`config.json`,
  `identity.json`) *and* the writes that follow them: two concurrent `init` otherwise both pass the
  checks and overwrite each other's identity, leaving an operator advertising a fingerprint that is
  no longer on disk.
- A sweeper runs every 60 s: deletes expired items, compacts `tokens.json`.
- `logLevel:"counters"` = never log a deposit address beyond its first 6 hex chars, never log a
  payload, never log an owner onion. `debug` relaxes this and MUST warn at startup.

## 6. Client integration (the five seams, plus the declared sixth)

1. **`RelayOutboundDelivery`** (new file under `lib/transport/`): seals the envelope and POSTs
   `/relay/deposit` through the existing `TorHttpClient` (SOCKS5). No new Tor plumbing: any onion is
   already dialable.
2. **`TransportProvider.postMessageOrFallback`**: after direct delivery fails with a *retryable*
   transport error, and only then, try the cached advertisement. Success -> the caller sees the same
   `true` it sees today, so `_markAsSent` runs and nothing else changes.
3. **`RelayPickupService`** driven from `SyncCoordinator` (`flushAllPending` and
   `onTorReconnected`): pickup -> unseal -> `InboundMessageRouter.handleMessage` -> ack. A 400 from
   the router is acked (poison item, dropped with a log); an exception is not acked (retry next tick).
4. **Settings**: `relayEnabled`, `relayContractJson`, `relayManifestJson`, `relayLastPickupAt` in
   `Settings`/`SettingsService` (the three dead placeholder fields were removed by the cleanup
   ticket; these replace them with glossary-aligned names).
5. **UI**: a Relay section in settings: manifest preview, pair by token/QR, usage, per-contact
   mailbox list with revoke, unpair.
6. **(declared conditional seam, now active)** advertisement publication in `buildProfile` +
   persistence of the peer's advertisement in `users.relayAdvertisement` (`chat_app.db` v18 -> v19).

Out of the v1 client footprint, on purpose: no new `messages.status` value (a message accepted by a
Relay is `sent`, as it is today when a peer's HTTP returns 2xx), no delivery receipt, no padding.

## 7. What the Relay learns, stated plainly

Sees: **which owner every item is for** — `index.json` maps `deposit -> ownerFingerprint`, the
Contract carries that owner's onion, and pickup is authenticated — the deposit address, the
ciphertext length, the arrival time, when the owner collects, and how many addresses a tenant has
(≈ how many contacts).

Does not see: sender, message type, `groupId`, file name or size, message id, or any plaintext; nor
**which contact** a deposit address was handed to (that mapping stays on the owner's device).

Can: drop, duplicate, delay (indistinguishable from an offline peer). Client-side duplicates are
harmless: `messages.id` is a primary key with tombstone-wins, and group messages additionally gate
on `(senderId, index)`.

Cannot: forge or reorder undetectably, read content, or link a deposit to a human without already
knowing that contact's address.

## 8. Explicit v1 limits (must appear in the user documentation)

- **First contact still needs both peers online once.** A session cannot be opened without the
  peer's prekey bundle, and that bundle comes only from a live `/profile` fetch. After the first
  contact, the Relay covers everything. (Briar Mailbox has the same property.)
- **Large attachments stay direct-only**: chunked file transfer is a WebSocket protocol between two
  live peers. Anything above the Contract's `maxItemBytes` is not relayed; it waits in the local queue.
- **Groups are fanned out by the sender**, one deposit per member at that member's Relay. A member
  without a Relay simply waits, exactly as today.
