# Prysm Relay

A **Relay** is a Prysm-speaking service that holds sealed messages for an
offline owner until that owner asks for them. It is not a central server:
anyone can run one, nobody needs one, and two peers that are online together
never touch one. It cannot see message contents — it stores opaque sealed
blobs — and it never sends on your behalf. Traffic is inbound-only (a sender
deposits, the owner picks up) and onion-only (HTTP over a Tor v3 hidden
service, port 80).

The normative wire contract is the
[protocol spec](../.scratch/relay/proto/relay-protocol-v1.md) ("the law",
versioned as `prysm-relay/1`). This page explains how the pieces fit
together; for byte-exact formats, always read the spec. Terms below follow
[CONTEXT.md](../CONTEXT.md): Relay, Mailbox, Contract, Pairing,
Advertisement, Pickup, Private Relay, Public Relay, Direct Delivery,
Prysm ID, Identity, Fingerprint.

## How a message reaches an offline peer

1. **Advertisement.** The owner's client publishes a signed Advertisement in
   its per-requester `GET /profile?requester=` answer, under key `relay`.
   Each requester gets its own deposit address (see below), and the block
   inherits `buildProfile`'s redaction policy: strangers and blocked peers
   learn nothing.
2. **Cache.** The sender's `PeerIdentityResolver` stores every fetched
   Advertisement in `users.relayAdvertisement` (`chat_app.db` v18 → v19).
   The cache is verifiable offline — the owner's signature covers it — which
   is the whole point, since it is used exactly when the owner is gone.
3. **Direct Delivery first.** `TransportProvider.postMessageOrFallback` tries
   the peer's own hidden service. Only a *retryable transport* failure (the
   peer is unreachable, not refusing) triggers the relay path; a peer that
   answered and rejected the payload would reject the relayed copy too.
4. **Seal verbatim.** `RelayOutboundDelivery.tryDeposit` seals the exact
   envelope the direct path would have POSTed — no re-wrapping, no field
   changes — under `relay-sealed-1` to the recipient's long-term X25519 key,
   and deposits it at the cached address. The sender never identifies itself
   to the Relay. An accepted deposit completes the send exactly like a 2xx
   from the peer, so the message is marked `sent`; any relay failure lets the
   original transport error propagate and the message stays in the local
   pending queue for direct delivery.
5. **Pickup.** `SyncCoordinator.flushAllPending` runs Pickup first
   (also on Tor reconnect): `RelayService.pickupNow` collects items,
   unseals each with the owner's agreement key, and feeds the envelope to
   `InboundMessageRouter.handleMessage` byte-identical, so auth, dedup,
   `pending_auth`, FTS and notifications run unchanged.
6. **Ack.** An item the router accepted — or refused with 400 (poison, would
   wedge every future Pickup) — is acked and deleted. An item that failed
   locally (storage, lock) is left on the Relay and retried next tick.
   Pickup is non-destructive, so a crash mid-Pickup costs a repeat, never a
   message.

The envelope is not re-wrapped because the inbound pipeline decides
addressing: `_validateAddressedToLocal` answers 403 unless `receiverId` is
the recipient's own onion, so only the original envelope survives Pickup.

Proven live: a 656 B envelope deposited as a 1072 B sealed blob, picked up
7 s after the recipient came back (app *and* Tor killed), with the Relay
reporting `items=0 bytes=0` after the ack. See
[relay-offline-delivery-proof.png](relay-offline-delivery-proof.png).

## Addressing: one mailbox per contact

A deposit address is 32 random bytes, generated by the owner, one per
contact — `RelayService.ensureMailboxFor` creates and registers it on first
use. The set of registered addresses **is** the whitelist: the Relay answers
`mailbox_unknown` identically for "never existed" and "revoked", so probing
learns nothing. Revoking a contact is deleting its address (`revokeMailbox`
→ `delete`); rotation is `put` new + `delete` old. The Relay never learns
which human an address belonged to — the local contact label never leaves
the device. (A Mailbox in glossary terms is the owner's whole store; each
deposit address is one contact's door into it.)

## The seal

Each seal uses a fresh ephemeral X25519 keypair against the recipient's
long-term X25519 agreement key, then `HKDF-SHA256` with info
`prysm-relay-seal-1` to derive an AES-256-GCM key. There is deliberately no
outer signature: content authenticity already rides inside the envelope
(ratchet AEAD/AAD, `dm-signed-*`, `group-sender-1`), and an outer signature
would hand the operator an oracle to test candidate keys and confirm "X
wrote this" — the exact property the seal buys. The HKDF info differs from
the DM path's `hkdfInfoDhAead`, so a sealed blob can never be confused with
or replayed into a 1:1 session. For the exact bytes see the
[spec §1](../.scratch/relay/proto/relay-protocol-v1.md) — the only place the
seal is defined. Real-world cost: 656 B in clear → 1072 B sealed on Relay
disk. The seal lives in `packages/prysm_relay_protocol`, not in
`lib/crypto`, so the app's crypto surface is untouched.

## Endpoints at a glance

One row per endpoint; the normative definitions, bodies and error codes are
[spec §3](../.scratch/relay/proto/relay-protocol-v1.md).

| Endpoint            | Who authenticates        | Purpose                                    |
|---------------------|--------------------------|--------------------------------------------|
| `GET /relay/manifest` | nobody (public, signed) | show who the Relay is before Pairing       |
| `POST /relay/pair`  | setup/invite token + owner signature | establish a Contract             |
| `POST /relay/mailbox` | owner signature        | register, disable, delete or list addresses |
| `POST /relay/deposit` | knowledge of the deposit address alone | store one sealed blob        |
| `POST /relay/pickup` | owner signature         | collect waiting items (non-destructive)    |
| `POST /relay/ack`   | owner signature          | delete collected items                     |
| `POST /relay/status` | owner signature         | Contract, usage, limits, server time       |
| `POST /relay/unpair` | owner signature         | delete tenant, Mailboxes and items         |

The sender never signs and is never identified: deposit authorization is
knowledge of the address (Signal's delivery-token pattern).

## Pairing and the Contract

Pairing exchanges proofs: the owner signs over the Relay's Fingerprint, its
own Fingerprint, a single-use token and a timestamp; the Relay answers with
a Contract signed by its own Identity. The client refuses a Contract whose
`relayFingerprint` does not match the manifest it paired against, and
re-pairing with the same Identity returns the same tenant with a new
version. `relayIdentityJson` is mandatory in the manifest: a Fingerprint
alone is a claim, and without the public key neither the manifest nor the
Contract signature could be verified. `overflow: reject` is the only v1
policy — a full Mailbox refuses new deposits instead of silently dropping
the oldest, because losing the newest message is visible to the sender while
losing the oldest is visible to nobody. Operator-side details (tokens, torrc,
storage) live only in the
[server README](../packages/prysm_relay_server/README.md).

## Threat model

The Relay **sees**: which account each item belongs to — `index.json` maps
every deposit address to an `ownerFingerprint`, the Contract carries that
owner's onion, and Pickup is authenticated — plus the deposit address, the
ciphertext length, arrival and collection times, and how many addresses a
tenant holds (≈ contact count). So for every stored item it knows *who it is
for*. It **does not see**: the sender, the message type, `groupId`, file
names or sizes, message ids, or any plaintext (audited on a stored blob: only
the keys `alg, ciphertext, crypto, ephemeralPub, nonce, scheme`), and it
cannot tell **which contact** a deposit address was handed to — that mapping
never leaves the owner's device. It **can** drop, duplicate or delay —
indistinguishable from an offline peer, and harmless: `messages.id` is a
primary key with tombstone-wins, so client-side duplicates collapse. It
**cannot** forge or undetectably reorder, read content, or link a deposit to a
human without already knowing that contact's address.

One honest consequence, from the
[ADR](adr/0001-relay-sealed-mailbox.md): the outer seal has **no forward
secrecy** — an ephemeral key against a long-term Identity key. An adversary
who records Relay traffic and later compromises the recipient's Identity
learns *who wrote to whom and when*, but not the content, which the inner
ratchet still protects. Length, timing, contact count and Pickup identity
stay visible; padding (`blockSize`, declared in the Contract from v1 but
always 0) and decoy Pickups are deferred, not forgotten.

## v1 limits

- First contact still needs both peers online once: the prekey bundle comes
  only from a live `/profile` fetch, and no session opens without it.
- Large attachments stay direct-only: chunked transfer is a WebSocket
  protocol between two live peers, so anything above `maxItemBytes` waits in
  the local queue.
- Groups fan out on the sender: one deposit per member at that member's
  Relay, and a member without a Relay waits as today.
- No delivery receipts: confirming arrival would reveal when the recipient
  came back online.
- No padding (`blockSize: 0`): lengths leak; the Contract declares the field
  now so padding can switch on without breaking the wire.
