# Relays deliver into per-contact sealed mailboxes

Status: accepted

Prysm needed store-and-forward so a recipient can receive while offline, without handing a third
party the social graph that our outer message envelope carries in plaintext (`senderId`,
`receiverId`, `type`, `groupId`, `fileName`, `fileSize`). We decided that a **Relay** addresses
deliveries by an opaque 32-byte **deposit address** — one per contact, generated by the owner and
published in the already per-requester `GET /profile?requester=` response — and that the sender
deposits the *original, unmodified* message envelope wrapped in a `relay-sealed-1` seal (ephemeral
X25519 → HKDF-SHA256 with info `prysm-relay-seal-1` → AES-256-GCM) addressed to the recipient's
long-term X25519 agreement key. The Relay therefore sees a capability, a ciphertext length and an
arrival time, and nothing else.

## Considered options

- **Envelope in the clear** (simplest, zero crypto work): rejected because a Public Relay would
  become a metadata honeypot — sender, recipient, message kind, file names and timing for every
  message it carries.
- **One deposit address per mailbox**: rejected because it makes the user's whitelist impossible to
  express (nothing distinguishes contacts) and turns any leaked address into permanent flooding
  rights.
- **A new ratcheted layer for the seal**: rejected because it would require sender/recipient session
  state for a layer that only protects metadata; the inner ratchet already protects content.
- **Signing the seal**: rejected because a signature is testable against candidate public keys,
  handing an operator an oracle to confirm "X wrote this" — the exact property the seal buys.
  Authorization to deposit is knowledge of the address (Signal's delivery-token pattern);
  authenticity remains with the inner envelope.

## Consequences

- **The inbound pipeline is untouched.** Unsealing yields the byte-identical envelope, so
  `InboundMessageRouter.handleMessage` runs auth, dedup, `pending_auth`, FTS and notifications
  exactly as for direct delivery, and `receiverId` still satisfies `_validateAddressedToLocal`.
- **The outer seal has no forward secrecy.** It uses an ephemeral key against a long-term identity
  key, so an adversary who records Relay traffic and later compromises the recipient's identity
  learns *who wrote to whom and when* — but not the content, which the inner ratchet still protects.
- **Revocation is address rotation**, and the Relay never learns which human an address belonged to.
- **`relay-sealed-1` must stay domain-separated** from the 1:1 DM path: its HKDF info differs from
  `hkdfInfoDhAead`, so a sealed blob cannot be replayed into `decryptFromPeer`.
- The seal lives in `packages/prysm_relay_protocol`, not in `lib/crypto`, keeping the app's crypto
  surface unchanged.
- Length, timing, contact count and pickup identity remain visible; padding (`blockSize`, declared in
  the Contract from v1 but always 0) and decoy pickups are deferred, not forgotten.
